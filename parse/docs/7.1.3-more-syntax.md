# Missing AST syntax nodes

This is about the `ASTBuilder` in builder.js compared with the declared tokens and node types.

The current implementation is a **structural skeleton**. It successfully handles the specific features we've focused on (HTML, basic headings, fenced code, simple inlines), but large sections of the Markdown specification are currently stubbed out or missing entirely.

### 1. Missing Block Structures
The following block types have tokens defined but no parsing logic in `consumeChunk`:
*   **Lists**: `BulletListMarker`, `OrderedListMarker`, `TaskListMarker`. There is no logic for list item creation, nesting, or tight/loose lists.
*   **Blockquotes**: `BlockquoteMarker`. No logic to push/pop blockquote containers.
*   **Tables**: `TablePipe`, `TableDelimiterRowMarker`. No table row/cell parsing.
*   **Thematic Breaks**: `ThematicBreak` token is ignored.
*   **Frontmatter**: `FrontmatterOpen/Close` tokens are ignored.
*   **Formulas**: `FormulaBlock` tokens are ignored.
*   **Setext Headings**: Only ATX (`#`) headings are supported; Setext underline style is missing.

### 2. Missing Inline Features
*   **Images**: `ImageMarker` (`!`) is not handled (Links are, but images are distinct).
*   **Autolinks**: `AngleLinkOpen`, `RawURL`, `EmailAutolink` etc. are missing.
*   **HTML Special Blocks**: `HTMLComment`, `HTMLCData`, `HTMLDocType`, `XMLProcessingInstruction` are missing (only standard Tags are handled).
*   **Escapes & Entities**: `Escaped` tokens and specific entity tokens (`EntityNamed`, `EntityDecimal`) fall through to the default text handling, which is *functionally* okay for text content but might miss semantic nuances or unescaping requirements.

### 3. Structural Simplifications
*   **Container Initiation (Phases 3 & 4)**: The code explicitly notes these phases are "Deferred". Currently, block nesting is handled ad-hoc (e.g., "if matching ATXHeading, pop paragraph"). A robust parser needs a proper container state machine to handle complex nesting like a list inside a blockquote inside a list.
*   **Paragraph Continuation**: The logic assumes `NodeTypes.Document` means "start a paragraph". It doesn't robustly handle lazy continuation lines or interrupting paragraphs with other blocks.

### Recommendation
To move from prototype to production parser, I recommend tackling **Lists and Blockquotes** next. These introduce the most structural complexity (recursive nesting) and will force the implementation of the "Container Initiation" phase.


# Blockquotes Implementation Plan

Here is a plan to specifically tackle **Blockquotes**, adhering strictly to the current single-pass, streaming loop architecture inside `consumeChunk` without hallucinating or referencing outdated "Phase" logic.

We will focus purely on manipulating the active stream state via the `blockStack` based on the sequence of `BlockquoteMarker` instances vs the depth of already existing `BlockquoteNode` layers on the stack.

### Context Recap:
1. `scan0` is returning raw `BlockquoteMarker` (length 1) + optionally interleaved with `Whitespace`.
2. The semantic unit is a paragraph-sized chunk of tokens provided to `consumeChunk(tokens)`.
3. In `consumeChunk`, we iterate over `tokens`. When we encounter `BlockquoteMarker` instances, we must structurally align the `blockStack` to match the count of these "prefix" markers on that line.
4. Any paragraph/node already deep on the stack needs to interact gracefully with the dedent/indent rules, exactly as `ListNode` does.

---

### Implementation Plan: Blockquotes

**Goal:** Modify builder.js to correctly instantiate, nest, and lazily construct/dedent `BlockquoteNode` purely via AST stack matching in `consumeChunk`.

#### 1. Add Stack Alignment Tracking (`blockStack` Depth Analysis)
Instead of a separate "initiation phase," we handle `BlockquoteMarker` tokens within the inline stream loop exactly like the list markers. 

When encountering `Tokens.BlockquoteMarker`:

- **Case A: Deeper marker depth than stack depth:** If we see a `BlockquoteMarker` and the current top block on the stack isn't deep enough in blockquotes (or is an unrelated block like a Paragraph), we push a new `BlockquoteNode` onto the `blockStack`. 
  - If `activeBlock` is a `ParagraphNode`, we will *pop* it, push the new `BlockquoteNode`, and wait for the rest of the stream to spawn the internal block (like another inner paragraph).

- **Case B: Same depth (Continuation):** If the sequence of `BlockquoteMarker` tokens aligns with the existing nested `BlockquoteNode` levels on the stack, we simply skip the markers, advancing `pos`, maintaining the current deep blocks (which permits paragraph continuations across wrapped lines).

- **Case C: Dedent (Lazy Continuation vs Severance):** If we encounter a newline *without* enough `BlockquoteMarker` tokens on the *next line*, the current logic inside `consumeChunk` should safely allow any already-open `ParagraphNode` on top of the blockquote to either passively absorb the text (Lazy Continuation) OR, if a different structural marker appears, we pop back down the stack until we align. 

#### 2. Specific Logic Insertion in `consumeChunk`
I will replace the STUB inside `builder.js` with the following routine:

1. **Pre-Filter:** Identify if `activeBlock.type === NodeTypes.Paragraph`. 
   - A blockquote immediately interrupts a paragraph across chunks. If a `BlockquoteMarker` appears at the start of a logical line, it breaks the outer paragraph. We `blockStack.pop()` the paragraph.
2. **Nesting Traversal:** Since a single line could have multiple markers like `> > > text`, we can safely loop or track them. 
   - *However*, `consumeChunk` processes exactly *one token at a time* in its main `for` loop. 
   - To align the single token `BlockquoteMarker`, we do a stack look-down:
      - How many `BlockquoteNode` exist in the *current path*?
      - To avoid maintaining state outside the loop, we check if the *current open structural boundary* expects a blockquote.
   - Wait! Since the tokens arrive sequentially (e.g. `[BlockquoteMarker, Whitespace, BlockquoteMarker, Whitespace, InlineText]`), we can dynamically resolve depth one token at a time.
   - If `activeBlock.type !== NodeTypes.Blockquote`, we `_pushBlock(new BlockquoteNode(...))`.
   - Wait, if `activeBlock` *is* a `Blockquote`, does this token *mean* we are nesting? 

**Refined Token-by-Token approach:**
- Since `scan0` provides `BlockquoteMarker` sequentially for nested quotes (e.g., `>` followed by `>`), we need to check if the current marker corresponds to an ALREADY explicitly opened blockquote at that index level for this line.
- Since we process token by token, this is slightly trickier because paragraph lazy continuation relies on *ignoring* missing blockquotes. 
- *Better approach inside the single-pass loop:* When we process a structural newline inside the chunk (or at chunk start), we can peek ahead and count the consecutive `BlockquoteMarker`s before processing the line's content.

**Proposed Strict Single-Pass Logic (without lookahead):**
Since `builder.js` operates token-by-token:
```javascript

        // If a new BlockquoteMarker arrives, it interrupts any existing paragraph 
        // that belongs to a SHALLOWER structural level.
        // For simplicity, pop the active paragraph.
        this.blockStack.pop(); 
        activeBlock = this._getActiveBlock();
    }

    // We need a mechanism to know if THIS token matches an ALREADY OPEN blockquote

    if (activeBlock.type !== NodeTypes.Blockquote) {
        this._pushBlock(new BlockquoteNode(this.context, pos));
    } else {
        // If it IS a Blockquote, we must determine if this specific `>` token is 
        // confirming the existing container or starting a new nested one.
```

To make it flawless without complex state, I propose we add a transient integer `lineQuoteDepth = 0` at the top of the inline stream loop (resetting to `0` whenever `kind === Tokens.NewLine` is encountered).

When a `BlockquoteMarker` is parsed:
1. `lineQuoteDepth++`.
2. Count the number of `BlockquoteNode` instances currently open in `this.blockStack`.
3. If `lineQuoteDepth > openQuoteNodeCount`, push a *new* `BlockquoteNode` onto the stack (handling the nested `> >` case natively).

**Summary of Changes:**
1. Introduce a block-scope variable `let lineQuoteDepth = 0;` at the start of `consumeChunk` and reset it under the `NewLine` handler.
2. In the `Tokens.BlockquoteMarker` block:
   - Pop any active `ParagraphNode`.
   - Increment `lineQuoteDepth`.
   - Count existing `BlockquoteNode`s in `this.blockStack`.
   - If `lineQuoteDepth > existing`, push a new `BlockquoteNode`.
   - Skip token `continue;`.

This inherently handles standard quotes, nested quotes (`>>`), and spaced nested quotes (`> >`), entirely within the existing streaming paradigm without multi-pass phases.
