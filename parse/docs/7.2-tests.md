# Annotated AST Test Runner Implementation Plan

The AST test runner verifies the structural properties of nodes generated by the parser. Unlike the token scanner verifier that checked linear streams, the AST verifier must navigate a hierarchy to find nodes that start at specific string offsets and evaluate structural property assertions against them.

## Core Principles

1.  **Strict Positional Mapping:**
    *   Markers (`1`, `2`, `A`, `B`) define an exact character offset relative to the start of the source line.
    *   Each marker is bound to one or more AST nodes whose `start` offset matches the exact absolute position (line start offset + marker column).

2.  **Targeted Constraint Evaluation:**
    *   Assertion lines (`@1 Heading level=1`) do not describe the whole node. They define **constraints**.
    *   The runner is not a formatter that dumps the AST. It evaluates the constraints defined in the assertion against the properties of the node it found.
    *   Only properties explicitly mentioned in the assertion are evaluated.

3.  **Correct Diagnostic Synthesis:**
    *   If the constraints are satisfied, the assertion passes silently.
    *   If an assertion fails, the runner synthesizes what the `@` line *should* have been based on the node's actual properties, replacing the failed assertion with the actual data to generate a diff.

## 1. Finding Nodes at Positions

Since the AST is a tree, but markers represent absolute string offsets, the runner must locate nodes securely.

*   **Absolute Offset Calculation:** `absolute_offset = block_start_offset + line_start_offset + marker_column`.
*   **Search Strategy:** Perform a depth-first traversal of the AST.
    *   If a node's `start` property exactly equals the `absolute_offset`, it is added to the candidate list for this marker.
    *   The search must traverse into `children` because structural containers (like `Heading` or `Emphasis`) and their first child (like `Text`) often start at the exact same offset.

## 2. Assertion Constraints Parsing

The runner needs a robust parser for the `@` lines, adapted from the token verifier but expanded for AST properties.

### Syntax
`@<MarkerID> <NodeType> [key=value]* ["TextContent"]?`

### Parsing Strategy
1.  **Extract ID:** Read the identifier directly after the `@`.
2.  **Extract Type:** The first word defines the `NodeType` (e.g., `Heading`, `Text`, `List`).
3.  **Extract Properties:** Iterate over key-value pairs (e.g., `level=2`, `isOrdered=true`).
4.  **Extract Text:** Use a robust quote-sniffer (like in `verify-tokens.ts`) to extract trailing JSON-encoded strings as the exact text constraint.

### Constraint Structure
An assertion parses into an object:
```javascript
{
  id: "1",
  type: 3, // NodeTypes.Heading
  constraints: {
    level: 2
  },
  textConstraint: null // or " Heading 2"
}
```

## 3. Resolving Ambiguities (The "Same Offset" Problem)

In an AST, multiple nodes can start at the exact same character. For example:
`# Hello`
At offset 0, we have both a `Heading` node and its inner `Text` node (assuming the parser is fixed to drop the `#`).

If the user writes:
```markdown
# Hello
12
@1 Heading level=1
@2 Text "Hello"
```
The test needs to map multiple `@` constraints to nodes that might share the same offset.

### Resolution Rules:
1.  If multiple nodes share an offset, the runner attempts to match the constraints of the `@` line against the candidate nodes.
2.  If an `@` line asserts `NodeType.Heading`, it binds to the `Heading` node.
3.  If an `@` line asserts `NodeType.Text`, it binds to the `Text` node.

## 4. Execution and Diff Generation

When a test is executed on an annotated block:

1.  **Compile Inputs:** Parse the position line for marker characters and their offsets. Parse the `@` lines into constraint objects and bind them to the marker offsets.
2.  **Run Parser:** Generate the AST for the entire document buffer.
3.  **Verification Loop:**
    *   For each marker character defined in the position line:
        *   Find AST nodes that start at its calculated absolute offset.
        *   Find the defined assertion(s) for this marker.
        *   Verify the node satisfies the defined constraints (`type`, `text`, specific keys).
4.  **Synthesis on Failure:**
    *   If a constraint fails, or if no node exists at the offset, the test fails.
    *   The runner must synthesize a new chunk of output showing the actual state.
    *   The synthesized `@` line must include all keys the user attempted to assert, plus the core identity of the actual node found (its `type` and `text`).
5.  **Output Diff:** Strict equality check between the normalized input string block and the synthesized string block.
