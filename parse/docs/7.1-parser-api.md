# AST Parser Architecture

This document describes the design of the MixPad Abstract Syntax Tree (AST) Parser. The parser is the final stage of processing. It takes the text and the tokens produced by the semantic scanner, and builds a standard, readable object tree.

## The Goal
The goal of the parser is to stream the semantic tokens and produce a standard tree of objects (the AST). This tree must be easy to read and intuitively structured for anyone wanting to build a renderer, editor tool, or linter. At the same time, the parser itself must allow for fast incremental updates safely.

## 1. Incremental Streaming & Stack-Based Construction

The parser works as a state machine. It does not parse the whole string from scratch every time you type. 

1.  **Reading Tokens**: It reads tokens one by one from the semantic scanner output.
2.  **The Context Stack**: The parser keeps a "stack" of currently open nodes (like a `Document`, holding a `List`, holding a `ListItem`). 
3.  **Opening Nodes**: When a token indicates the start of a block (like `FencedOpen` for a code block), the parser creates a `CodeBlock` node, adds it to the current parent's `children`, and pushes it onto the stack so it becomes the new active parent.
4.  **Closing Nodes**: If a token arrives that does not belong in the current node (for example, the parser is in a code block and sees a `FencedClose` token, or is in a list item and sees a token with zero indentation), it pops the current node off the stack and marks its `end` position.
5.  **Safe Reparse Points**: During live editing, `scan0` marks certain tokens as `IsSafeReparsePoint`. Instead of replacing the whole AST when a user types, the parser finds the closest safe point before the edit, resumes reading from the semantic scanner, matches its stack state to the old tree's state, and only updates the localized branches of the AST that actually changed.

## 2. Low-Allocation Model with On-Demand Getters

MixPad is designed to be fast and use very little memory. Standard parsers usually slice up the input string and store the pieces directly inside the AST objects. This creates thousands of temporary strings and slows things down.

Instead, MixPad AST nodes are simple objects that store numerical positions (`start` and `end`).

### Shared Parse Context
To quickly provide logical text back to the caller without making the caller pass the document text all around, every single AST Node is given a reference to a single lightweight context object during parsing.

```javascript
const context = { sourceText: "# Hello World" };
```

### Transparent `get` Properties
Where logical text or extracted properties are needed, the AST classes use JavaScript getter methods (`get text()`). A caller typing `node.text` will seamlessly get the logical string back, unaware that work happened behind the scenes.

**Caching and Formatting:**
Because computing these logical strings isn't always cheap (it involves decoding HTML entities, handling escaped characters like `\*`, and collapsing multiple spaces or newlines), the results are cached. 

If a caller requests `node.text`, the getter will:
1. Check if the value is already cached. If yes, return it immediately.
2. If not, extract the raw slice using `this.start` and `this.end`.
3. Process the text (decode `&amp;` to `&`, turn newlines into spaces).
4. Store the processed string in `this._text` and return it.

This means if an editor never needs to read the text of an open paragraph, the engine never wastes CPU cycles decoding it.

### Node Property Typings
Instead of using strings for `node.type` (which are slower for engines to compare), we will use a separate file to define Node Types as numerical enums.

```javascript
// Integer match is considerably faster than string matching in a hot loop
if (node.type === NodeTypes.Paragraph) { ... }
```

## 3. List of All AST Nodes

Below is the complete set of standard AST nodes the parser will generate, mapped directly to the tokens produced by the semantic scanner. Every node shares a base set of properties: `type` (numeric enum), `start` (number), `end` (number), and `children` (array).

### Block-Level Nodes
These nodes form the main vertical structure of the document.

*   `Document`: The root of the tree.
*   `Paragraph`: A standard block of flowing inline text.
*   `Heading`: Created from `ATXHeadingOpen` or `SetextHeadingUnderline`. It contains inline children. It will provide a transparent getter `node.level` (1-6) derived from the starting characters.
*   `Blockquote`: Created from `BlockquoteMarker`. Wraps other block nodes.
*   `List`: Created when list markers appear. Wraps `ListItem` nodes. Provides an `isOrdered` getter.
*   `ListItem`: Wraps the content inside a list. Handles indentation logic to know when it closes.
*   `FencedCodeBlock`: Created from `FencedOpen`. Contains `Tokens.FencedContent`. Provides a `node.language` getter to extract the info string if present.
*   `HtmlBlock`: Wraps raw HTML tags when they sit at the block level according to CommonMark HTML block rules.
*   `ThematicBreak`: Created from `ThematicBreak`. Represents horizontal rules like `---` or `***`. Does not contain children.
*   `Table`: Created when table rows are detected. Wraps `TableRow` nodes.
*   `TableRow`: Wraps `TableCell` nodes.
*   `TableCell`: Wraps inline content.
*   `Frontmatter`: Wraps the raw TOML or YAML content found at the beginning of a document.
*   `FormulaBlock`: Math blocks bounded by `$$`.

### Inline-Level Nodes
These nodes live horizontally inside Blocks.

*   `Text`: A leaf node storing boundary offsets. Provides the `node.text` getter that cleanly collapses whitespace, decodes entities (`EntityNamed`, `EntityDecimal`), and handles backslash escapes.
*   `Emphasis`: Italic text. Usually surrounds `Text` nodes.
*   `Strong`: Bold text. Usually surrounds `Text` nodes.
*   `Strikethrough`: Crossed out text.
*   `Link`: Provides `node.url` and `node.title` getters that unescape their respective destination and title values dynamically. Contains children representing the visible link text.
*   `Image`: Same shape as `Link`, but rendered as an image reference.
*   `InlineCode`: Raw code inside single backticks.
*   `Autolink`: Bounded by angle brackets, or raw URLs detected in the text. Provides a getter for `node.url`.
*   `HtmlTag`: Inline HTML open or close tags. Provides `node.tagName` and `node.attributes` getters.
*   `HtmlComment`: Contains the text of an HTML comment.
*   `HtmlCData`: Represents `<![CDATA[...]]>`.
*   `HtmlDocType`: Represents `<!DOCTYPE ...>`.
*   `XmlProcessingInstruction`: Represents `<?php ... ?>`.
*   `InlineFormula`: Math bounded by `$`. 

This node vocabulary covers every token emitted by the scanners and forms a coherent, high-speed AST architecture ready for any CommonMark environment.
