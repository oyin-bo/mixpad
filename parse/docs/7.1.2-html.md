# AST HTML Integration Plan

Following the zero-allocation, first-class HTML citizenship design of MixPad, this document defines the intended refactor for integrating granular Phase 1 HTML tokens directly into a high-fidelity, DOM-like Abstract Syntax Tree (AST).

## Background and Motivation

Unlike typical Markdown parsers that treat HTML constructs as single opaque string blocks, MixPad's scanner dissects every HTML piece (opening tag markers, tag names, attribute names, attribute values, and closing makers) natively. We must mirror this design upward into the AST architecture. 

Currently, the AST erroneously treats HTML under standard Markdown-like assumptions: distinguishing an `HtmlBlockNode` vs an `HtmlTagNode` while discarding intermediate tokens like attributes altogether. If HTML is a first-class citizen in MixPad, it must be mapped accurately to a structured element concept similar to `HTMLElement` in the DOM.

## 1. Unified `HtmlElement` Node Structure

We will delete the fragmented definitions (`HtmlBlockNode`, `HtmlTagNode`) and replace them with a unified **`HtmlElement`** node. An HTML element requires no artificial "block" vs. "inline" distinctions at the structural level. Both an inline `<span>` and a structural `<div>` are fundamentally the same node type in a parsing tree.

### HTMLElementNode

It should include tagName, attributes, children.

The children can be initialised as null for empty nodes to conserve memory.

## 2. Contiguous Parsing Loop in `builder.js`

In Phase 5 of the streaming parser inside `builder.js`, when we encounter an `HTMLTagOpen`, we shouldn't arbitrarily push it as an empty "tag" to an unresolved inline stack. 

The scanner already ensures consecutive output for valid HTML internals. We will execute an inner consumption `while` loop that resolves the entire opening tag header immediately without mutating parent state.

### Loop Responsibilities:
1. **Initialize:** Encounter `HTMLTagOpen` (length 1). Instatiate `HtmlElementNode`.
2. **Tag Name:** Read `HTMLTagName`, record the string bounds into `node.tagName`. 
3. **Attributes:** Loop through following attribute tokens (`HTMLAttributeName`, `HTMLAttributeValue`, skipping quotes and equals) binding pairs into the `node.attributes` array.
4. **Resolution:** Wait for `HTMLTagClose` or `HTMLTagSelfClosing`.

*(If the `HTMLTagOpen` token has a length of `2`, meaning it was literally parsed as a closing tag `</`, we skip building and instead pop the actively matched container out of the overarching `blockStack`.)*

## 3. Void Elements & Structural the Block Stack

The final and most critical capability of first-class HTML integration is naturally deciding if the `HtmlElementNode` can accept children (acting as a tree structure context) or if it's strictly a leaf node.

We will leverage the existing scanner utility `isVoidElement` from `scan-html-tag.js`, which securely pattern matches void tags via byte lengths arrays (identifying `br`, `hr`, `img`, `meta`, etc.) directly on the text chunk without allocating strings.

1. Once the `node.tagName` bounds are secured, we call `isVoidElement(context.sourceText, tagStart, tagLength)`.
2. If `true`, we keep the note that the node is self-closing. We also note it if we explicitly hit the `HTMLTagSelfClosing` token ending.
3. If not self closing, the HTML tag structurally demands content. We append it to its parent naturally but also push it **squarely onto the main `blockStack`**.
4. By sitting directly on `blockStack`, all subsequent parsed Markdown tokens and inner HTML elements natively resolve into the HTML Element's `children` array until a closing `</` token matches its tag name.

By unifying HTML as a primary container pushing to the block stack, MixPad enables fluid, DOM-fidelity parsing.

## 4. Malformed HTML & Error Recovery

HTML in the wild is often malformed (e.g., overlapping tags like `<b><i></b></i>` or missing closures like `<table><tr><td>`). Browsers handle this via complex, node-cloning algorithms (HTML5 Adoption Agency Algorithm). To maintain MixPad's zero-allocation and high-performance constraints, the AST builder will implement lightweight structural resilience:

1. **Pop-Until-Match**: When a closing tag is encountered, the builder scans upward through the active stack. If a matching opening tag is found, all unclosed intermediate nodes (the overlapping tags) are implicitly closed and popped from the stack alongside the matched tag. This safely unwinds the stack without heap-heavy node cloning constraints.
2. **Orphan Rejection**: If a closing tag is encountered but no matching parent exists anywhere in the active stack, it is treated as an orphan. The builder simply discards the closing tag (or degrades it to a text node), preventing it from maliciously collapsing the regular document structure.
3. **Implicit Auto-Close**: For sibling elements that implicitly close each other in HTML5 (such as `<p>` followed by `<p>`, or `<li>` followed by `<li>`), the builder can automatically pop the preceding container if it encounters a mutually exclusive open tag, mirroring basic HTML5 implied end tags without the overhead of a full DOM parser.
